# Цветочный магазин — настольное приложение на JavaFX

Настольное приложение для управления заказами цветочного магазина с графическим
интерфейсом на JavaFX. Это продолжение проекта из контрольной работы №1:
предметная область, сущности, бизнес-правила и база данных те же, консольный
интерфейс заменён на JavaFX, работа с данными идёт напрямую через JDBC
с PostgreSQL.

Контрольная работа №2: разработка настольного JavaFX-приложения.

## Описание предметной области

Система моделирует работу цветочного магазина: ведение базы клиентов, 
каталога букетов и обработку заказов на их покупку и доставку.

### Сущности

- **Customer (Клиент)** — участник системы, оформляющий заказы.
- **Bouquet (Букет)** — товар из каталога магазина.
- **BouquetOrder (Заказ букета)** — основная сущность варианта, связывает
  клиента и букет, отслеживает статус выполнения.

### Статусы заказа (OrderStatus)

| Код | В интерфейсе | Значение |
|---|---|---|
| `NEW` | Новый | заказ создан |
| `CONFIRMED` | Подтверждён | подтверждён менеджером |
| `IN_DELIVERY` | В доставке | передан в доставку |
| `DELIVERED` | Доставлен | доставлен |
| `CANCELLED` | Отменён | отменён |

## Архитектура

```
FXML (вид) → Controller → Service → Repository (JDBC) → PostgreSQL
```

| Слой | Пакет / каталог | Назначение |
|---|---|---|
| View | `resources/fxml`, `resources/css` | Разметка окон и оформление |
| Controller | `flowershop.controller` | Обработка действий пользователя, связь формы и сервисов |
| Service | `flowershop.service` | Бизнес-правила и проверка вводимых данных |
| Repository (DAO) | `flowershop.repository` | SQL-запросы через JDBC |
| Model | `flowershop.model` | Сущности предметной области |
| DTO | `flowershop.dto` | Строка таблицы заказов, условия фильтра, статистика |
| Exception | `flowershop.exception` | Собственные исключения |
| Util | `flowershop.util` | Подключение к БД, диалоги, форматирование, фоновые задачи, экспорт |
| Database | `db/` | Скрипты создания таблиц и тестовые данные |

Основные правила:
- SQL находится только в классах `*RepositoryJdbc`, в контроллерах его нет;
- репозитории и сервисы создаются в одном месте — `AppContext`, контроллеры берут сервисы оттуда;
- запросы к БД выполняются в фоновом потоке (`FxTasks`), поэтому окно не «зависает»;
- все исключения обрабатываются в одном месте — `DialogHelper.showError`.

## Требования для запуска

- **Java 21** (JDK)
- **Maven** 3.9+
- **Docker** с поддержкой `docker compose` (для базы данных)

Проверка версий:
```bash
java --version
mvn --version
docker --version
docker compose version
```

## Установка и запуск

### 1. Создать файл с паролем базы данных

```bash
cp .env.example .env
printf 'DB_PASSWORD=%s\n' "$(openssl rand -hex 12)" > .env
cat .env
```

### 2. Настроить подключение приложения

```bash
cp src/main/resources/database.properties.example src/main/resources/database.properties
```

Откройте `src/main/resources/database.properties` и укажите:

```properties
db.url=jdbc:postgresql://localhost:55433/flowershop
db.user=flowershop
db.password=значение_DB_PASSWORD_из_файла_.env
```

Порт `55433` выбран, чтобы не конфликтовать с локальным PostgreSQL (5432).

### 3. Запустить базу данных

Запустите Docker Desktop, затем:

```bash
docker compose up -d --wait
docker compose ps
```

В колонке `STATUS` должно быть `healthy`. При первом запуске скрипты из
каталога `db/` выполняются автоматически: создаются три связанные таблицы
(`customers`, `bouquets`, `orders`) с ограничениями `PRIMARY KEY`, `FOREIGN KEY`,
`NOT NULL`, `UNIQUE`, `CHECK` и загружаются тестовые данные: 6 клиентов,
6 букетов и 12 заказов во всех пяти статусах.

### 4. Проверить состояние базы

```bash
docker compose logs db | grep initdb.d
docker compose exec db psql -U flowershop -d flowershop -c "\dt"
docker compose exec db psql -U flowershop -d flowershop -c "SELECT status, count(*) FROM orders GROUP BY status ORDER BY 1;"
```

### 5. Запустить приложение

```bash
mvn clean compile
mvn javafx:run
```

Если база недоступна, при запуске появится окно «Нет подключения к базе данных»
с подсказкой, что проверить.

### Остановка

```bash
docker compose stop        # остановить БД, данные сохраняются
docker compose down        # удалить контейнер, данные сохраняются в томе
docker compose down -v     # удалить контейнер и все данные БД (осторожно)
```

### Использование локального PostgreSQL вместо Docker

Приложение работает с любой базой, созданной скриптами из `db/`. Для локального
сервера создайте базу (`createdb flowershop`), выполните `db/01_schema.sql` и
`db/02_seed.sql`, и укажите в `database.properties` свои `db.url`, `db.user`
и `db.password`. Скрипт `01_schema.sql` начинается с `DROP TABLE`, не запускайте
его на базе с нужными данными.

## Связь с контрольной работой №1

Сохранены вариант, предметная область, сущности, схема базы данных и бизнес-правила
КР №1. Консольный интерфейс заменён на JavaFX, слои `model`, `repository`,
`service` и `exception` перенесены и доработаны под графический интерфейс
(проверка полей с указанием названия, JOIN-запрос для таблицы заказов,
агрегатные запросы для статистики).

## Функциональность

Главное окно состоит из четырёх вкладок: **Заказы**, **Клиенты**, **Букеты**,
**Статистика**. При переходе на вкладку данные перезагружаются.

### Заказы (основная сущность)

- таблица `TableView` с клиентом, букетом, количеством, суммой, статусом и датами;
  служебные идентификаторы не показываются;
- добавление, изменение (в том числе двойным кликом по строке), удаление с подтверждением;
- смена статуса: в списке предлагаются только допустимые переходы;
- в форме клиент и букет выбираются из выпадающих списков, сумма рассчитывается автоматически;
- обновление данных и экспорт текущей выборки в CSV.

### Поиск, фильтрация, сортировка заказов

| Возможность | Реализация |
|---|---|
| Поиск | по имени клиента, названию букета и сумме |
| Фильтр 1 | по статусу |
| Фильтр 2 | по периоду дат заказа (границы включаются) |
| Сортировка | выпадающий список (дата и сумма по возрастанию и убыванию, клиент по алфавиту) и клик по заголовку любого столбца |
| Сброс | кнопка «Сбросить» очищает поиск, фильтры и возвращает сортировку по умолчанию |

Поиск и фильтры работают поверх загруженных данных (`FilteredList` →
`SortedList` → `TableView`), условия описаны в `OrderFilter`.

### Клиенты и букеты

- полный CRUD с проверками и подтверждением удаления;
- клиенты: поиск по имени, email и телефону;
- букеты: поиск по названию и описанию, фильтр по диапазону цены.

### Статистика

Девять показателей и диаграмма по статусам, все рассчитываются агрегатными
SQL-запросами:

1. всего заказов;
2. всего клиентов;
3. букетов в каталоге;
4. выручка по доставленным заказам;
5. средняя сумма заказа;
6. минимальная сумма заказа;
7. максимальная сумма заказа;
8. самый популярный букет (по количеству в неотменённых заказах);
9. доля отменённых заказов;
10. круговая диаграмма: количество заказов по статусам.

### Экспорт

Кнопка «Экспорт в CSV» выгружает ровно то, что сейчас видно в таблице заказов
(с учётом поиска, фильтров и сортировки). Путь выбирается пользователем через
`FileChooser`. Формат: разделитель `;`, кодировка UTF-8 с BOM, поэтому Excel
корректно открывает кириллицу.

## Бизнес-правила

1. Нельзя создать клиента без имени, телефона или с некорректным email.
2. Email клиента уникален (без учёта регистра).
3. Нельзя создать букет без названия или с ценой ≤ 0.
4. Нельзя оформить заказ на несуществующего клиента или букет.
5. Количество букетов в заказе от 1 до 999.
6. Дата доставки не может быть раньше даты заказа; дата заказа не может быть в будущем.
7. Сумма заказа рассчитывается автоматически (цена букета × количество) и не может
   превышать 99 999 999,99. При изменении заказа сумма пересчитывается, только
   если изменился букет или количество.
8. Допустимые переходы статуса: `NEW → CONFIRMED → IN_DELIVERY → DELIVERED`,
   а также переход в `CANCELLED` из `NEW`, `CONFIRMED` или `IN_DELIVERY`.
   Из `DELIVERED` и `CANCELLED` статус изменить нельзя.
9. Доставленные и отменённые заказы нельзя редактировать.
10. Нельзя удалить букет, по которому есть незавершённые заказы; букет, который
    указан в заказах из истории, также удалить нельзя.
11. Нельзя удалить клиента, у которого есть заказы.

## Валидация

Все поля проверяются в сервисах до сохранения, пользователь видит название поля
и причину, а поле в форме подсвечивается красной рамкой.

| Поле | Проверка |
|---|---|
| Имя клиента | обязательное, до 150 символов |
| Телефон | обязательный, до 30 символов, допустимы цифры, пробелы и `+ ( ) -`, от 10 до 15 цифр |
| Email | обязательный, до 150 символов, формат `name@example.com`, уникальный |
| Название букета | обязательное, до 150 символов |
| Описание букета | необязательное, до 1000 символов |
| Цена | обязательная, больше 0, не более 99 999 999,99, не более двух знаков после запятой |
| Клиент, букет в заказе | должны быть выбраны и существовать в БД |
| Количество | целое число от 1 до 999 |
| Даты заказа и доставки | логическая корректность (см. правило 6) |
| Период в фильтре | дата «с» не позже даты «по» |

## Обработка ошибок

Приложение не завершается аварийно и не показывает пользователю stack trace.
Все исключения обрабатываются в `DialogHelper.showError`, технические подробности
записываются в журнал (slf4j).

| Исключение | Реакция в интерфейсе |
|---|---|
| `ValidationException` | предупреждение с названием поля и подсветка поля в форме |
| `BusinessException` | предупреждение с текстом нарушенного правила |
| `EntityNotFoundException` | сообщение «Запись не найдена» (например, удалена в другом месте) |
| `DatabaseConnectionException` | «Ошибка базы данных» с подсказкой проверить подключение |
| Прочие | общее сообщение о внутренней ошибке |

Если при сохранении формы возникает ошибка, диалог остаётся открытым, и пользователь
исправляет данные. Ошибки базы данных, которые приходят от PostgreSQL (нарушение
уникальности или внешнего ключа), переводятся в понятные сообщения по коду SQLState.
